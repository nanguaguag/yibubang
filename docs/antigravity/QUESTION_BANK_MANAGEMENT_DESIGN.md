问题边界：

1. 保存、发现题库、检查更新、下载、完整性校验耦合。
2. 同一列表的相同 URL 基本去重；不同 URL 含同一 bank_id 会抛错并使整次刷新失败，没有来源选择模型。
3. 只缓存清单元数据，临时下载包在检查结束删除；添加后保存/随后下载安装可能再次传输同一内容。
4. 顶部和单库按钮分别执行“检查”和“检查并安装”，入口名称、结果提示和用户预期不一致。
5. 本地合并改变文件与版本后，当前文件 hash 不等于上游 hash，不足以证明上游发布了新内容；允许自动更新也不应影响“有无更新”的判断。
6. 单个来源异常阻断其他来源结果；官方清单联网失败可退回内置配置，需明确缓存/离线状态，不能表述为已确认最新。

## 2. 推荐的三个实体

- 来源：一个发布清单 URL 或题库文件 URL。内置官方来源与用户添加来源采用相同模型。
- 已安装题库：由 bank_id 标识，记录内容版本、来源绑定和本地补充状态；同学科可以存在不同题库。
- 更新任务：一次检查或下载应用过程，可缓存产物、报告结果、重试和取消。

一份清单可提供多个题库，同一题库可被多个来源提供。每个已安装题库只有一个当前主来源，其他来源保留为候选。候选不自动交替覆盖内容，也不因为同名或同学科就认为是重复题库。

更新来源可以先保存为“待验证”；验证失败保留该状态，不宣称已绑定到特定题库。已有主来源修改时，旧绑定保持可用，新候选确认 bank_id/学科匹配后才切换。

## 3. 操作契约与界面

| 操作 | 网络/磁盘行为 | 是否改变已安装题库 |
| --- | --- | --- |
| 保存订阅 | 保存配置，做 URL 基本校验与去重；新增/修改来源标记待检查 | 否 |
| 检查更新 | 获取发布元数据/HTTP 变化线索；刷新远端状态 | 否 |
| 下载并更新 | 获取或复用更新包，校验，处理本地变更，安装 | 是 |
| 检查完整性 | 只检查本地 SQLite；显式运行完整扫描 | 否 |
| 重新下载 | 明确获取同一发布包，用于本地文件损坏后的恢复 | 是；本地有补充时先处理，不后台覆盖 |

“添加来源”和“从链接导入题库”作为两个明确意图：

- 添加来源只保存地址，可以继续使用题库。
- 从链接导入进行一次完整下载并识别题库；询问是否订阅以后更新，开启后复用本次已取得的元数据和包。

订阅页顶部“检查全部更新”与管理卡片上的单库“检查更新”调用相同流程，只改变范围。全局来源检查集中在订阅页，管理页保留题库级动作。检查完成显示来源结果，不能自动触发安装。

单库无更新时图标表示检查；已知有更新时显示“下载并更新”及版本提示。详情页展示当前主来源、最近检查时间和结果；完整性检查、重新下载放详情的更多操作，不占主要按钮位置。

自动设置分成“自动检查更新”与“发现更新后自动安装”，后者仅作用于可安全跟随上游的题库。本地有补充的库可自动检查并通知，需要用户处理后安装。保留当前检查间隔选择。

界面状态分别显示：已安装/未安装、本地有补充/跟随订阅、未检查/已是最新/有更新/需下载确认/检查失败。不能将“有更新”和“启用自动安装”合成一个布尔值。

## 4. 重复与来源冲突

- 相同规范化 URL：不重复添加，定位已有来源并提示“该订阅已存在”；保存时无网络请求。
- URL 规范化只做不改变请求含义的处理，保留路径大小写和签名查询参数，不能随意删参数或猜测镜像地址等价。
- 不同 URL、同一 bank_id：识别为同一题库的候选来源，不重复安装，不中断其他来源检查。默认保留已有主来源；用户可显式切换，必须确认学科/格式兼容。
- 同一 bank_id、来源内容不同：显示来源差异，不能按哪个请求先返回就覆盖。无法证明一致性的不同发布方不自动视作镜像。
- 同名或同学科、不同 bank_id：保留为不同题库；原始全局 question_id 继续共享用户状态。
- 删除来源仅取消后续检查，不删除已安装题库、答案或笔记。该源仍被题库绑定时显示解绑影响，并保留来源历史。

## 5. 轻量检查的能力与限制

### 发布清单来源（推荐）

仅请求小型 JSON，比较发布版本/发布标识和内容摘要。清单应提供 bank_id、学科编号、版本、下载 URL、包 SHA-256，以及可选的 SQLite SHA-256/稳定内容修订标识、大小、发布日期。

同一清单提供多个题库时，全局检查只请求一次；单库检查也复用同一来源的请求/缓存，应用范围仍仅为目标题库。支持条件请求和缓存，单次任务中并发请求合并。

没有增量包协议时，“只新增几道题”依然可能需要完整下载 ZIP；轻量检查与增量传输是两个独立能力。本提案先解决检查时不重复下载，不承诺未实现的二进制补丁。

### ZIP/SQLite 文件直链（兼容）

第一次需要识别文件时，可在用户选择“从链接导入”后完整下载；仅保存订阅不下载，标记待识别。已有绑定优先使用来源缓存。

后续用 HEAD 或条件请求获得 ETag/Last-Modified 等变化线索；成功的 304 可复用上次已验证结果。HEAD 不支持时可用条件 GET，在收到响应头后决定是否继续接收正文。

HTTP 变化线索只能说明远端资源可能变了，不能在未下载前承诺新版本、新增题量或数据库完整性。大小相同、没有更新时间、HEAD 失败都不能推断题库没有变化。

无清单且服务器不支持可靠条件检查时，显示“需下载确认”。用户选择后下载一次，计算摘要、读取元数据并复用该产物安装；自动安装已明确启用且本地无补充时，可以按同一受控任务继续执行。

用户的 database-3.0.0/clinical_final.sqlite.zip 是包含版本路径的发布文件地址。旧 URL 是否能发现未来版本取决于发布者是否会更新该地址；订阅这类旧版文件不等于订阅整个项目的未来发布。要稳定跟随新版，应使用持续更新的发布清单或发布者提供的固定 latest 地址，不能仅由客户端猜 URL 中的版本号。

## 6. 上游版本与本地补充独立记录

在可写用户库/应用元数据中记录以下信息，不修改正式内容库：

- 当前主来源、远端最近发现的发布信息。
- 最近一次已应用/已合并的上游发布标识及其摘要（base_release）。
- 本地补充标记、本地修订号、当前已安装文件摘要。
- 最近检查时间、最后成功检查时间、错误信息。

示例：订阅 3.0.0 + 本地补充 2；远端最新 3.1.0。

检查时比较“远端发布”与“最近已处理的上游发布”，不能只比较当前合并文件和上游文件的 hash；本地修订增加不会被解释为上游版本增加。

- 相同已应用上游发布：上游无变化；本地仍可显示有补充。
- 新上游发布且本地未补充：可下载校验并原子替换。
- 新上游发布且本地有补充：下载后展示新增/修改/移除差异，并选择“保留本地补充（合并）”“使用订阅版本（替换）”“暂不更新”。
- 合并默认复用现有能力：保留本地额外题与关系，同 question_id 采用订阅内容。界面必须说明此规则；会覆盖本地同 ID 题目修改时显示差异，不后台静默处理。
- 合并成功同样推进已处理的上游发布基线。重复检查不能对同一上游版本再次要求合并。
- 替换成功清除本地补充标记；用户答案、收藏、斩题、活动与笔记仍在用户库，保留不动。
- 上游版本倒退或同版本内容改变：呈现“来源内容变更/回退”，不单凭摘要不同自动降级。
- 旧安装记录没有来源基线时：通过已知清单摘要匹配或一次明确比较建立基线；无法确定时显示待比较，不把所有库误标最新或本地有补充。

## 7. 下载、校验与安装

流程：元数据检查 → 待下载/需确认 → 下载 → 校验 → 本地变更处理 → 暂存合并或替换 → 原子安装 → 更新履历。

任务缓存保留已验证包及其对应来源、发布标识/摘要；检查时已取得的包可直接用于后续安装，缓存限额/LRU 管理，运行中任务不被清理。同包同任务只下载一次。

同一已验证字节可复用校验结果，前提是复制/持久化后内容摘要吻合且校验规则未变；不能仅凭大小/时间相同跳过显式完整性检查。合并生成的新产物必须重新严格校验。来源清单 hash 属于发布校验，SQLite 完整性扫描属于结构/关系校验，二者不互相替代。

一个来源失败，只标记该来源/题库检查失败，其他来源结果正常发布；保留最近成功结果并标注过期，不能用缓存假称刚刚确认最新。检查履历与安装时间轴分开，检查不记为一次题库更新。

保持现有安装互斥、回滚、readOnly 正式文件、全局 question_id、SQLite ATTACH 聚合契约。题库内容只在新暂存文件中产生/合并，来源、任务与本地修订元数据均放应用可写区域。

医考帮 API 抓取入口仍明确称“同步题目”；它与订阅包下载更新保留不同来源能力，不能因统一界面而把全科 API 抓取描述为轻量检查。
